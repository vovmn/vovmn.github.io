# Проверка безопасности Immunolab

Дата проверки: 28 октября 2026 года.

## Исправлено

- Локальные `.env` удалены из текущего Git-снимка и закрыты через `.gitignore`;
  добавлены только безопасные `.env.example`.
- Удалено логирование пароля БД, access-токенов и отладочного состояния
  авторизации.
- JWT проверяется с фиксированным алгоритмом `HS256`, issuer и audience;
  сервер требует секрет длиной не менее 32 байт.
- Refresh-токен хранится в БД только как SHA-256, одноразово ротируется при
  обновлении сессии и отзывается при logout.
- Добавлены Helmet, ограничение размера JSON и rate limiting для API и
  авторизации.
- Nginx скрывает версию, ограничивает тело запроса и отдаёт CSP,
  `X-Content-Type-Options`, `Referrer-Policy` и `Permissions-Policy`.
- Административные маршруты защищены общей цепочкой `requireAuth` +
  `requireAdmin`; пользовательские назначения и ответы проверяются по `user_id`.
- SQL-запросы с пользовательскими значениями параметризованы.
- Составные FK запрещают записывать ответ в чужое назначение или выбирать
  вариант от другого вопроса.
- Production-зависимости backend и frontend обновлены: `npm audit --omit=dev`
  сообщает 0 известных уязвимостей.
- Production Docker-образы успешно собираются на Node 20/24; Nginx-конфигурация
  проходит `nginx -t`.

## Проверки

- Backend: 3 набора, 10 тестов, все пройдены.
- Проверена миграция старой локальной БД до версии `20261028_02`.
- Временный production backend-образ вернул `200` на `/health` и подключился к
  PostgreSQL.
- В staged Git-снимке не найдено известных паролей, API-токенов и маркеров
  приватных ключей.

## Оставшиеся риски

1. Старые development `.env` остаются в предыдущих Git-коммитах. Значения были
   слабыми, но production-секреты с ними не совпадают. Полная очистка требует
   согласованного `git filter-repo` и force-push; в рамках обычного обновления
   история не переписывалась.
2. Текущий сервер доступен по HTTP. Перед публикацией через FRP нужен TLS на
   внешней точке или reverse proxy, иначе медицинские и учётные данные могут
   быть перехвачены в сети.
3. Access-токен фронтенда хранится в `localStorage`. CSP снижает риск XSS, но для
   более строгой модели следует перейти на in-memory access token либо полностью
   HttpOnly cookie с CSRF-защитой.
4. Нет MFA и отдельного журнала административных действий. Это желательно до
   работы с реальными пациентами.
5. Резервные копии лежат на том же сервере; нужна зашифрованная внешняя копия и
   регулярная проверка восстановления.

Эта проверка не является сертификацией и не заменяет независимый pentest перед
обработкой реальных медицинских данных.
